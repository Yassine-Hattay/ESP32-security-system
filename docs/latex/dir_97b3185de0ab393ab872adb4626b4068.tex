(See the README.\+md file in the upper level \textquotesingle{}examples\textquotesingle{} directory for more information about examples.)

{\ttfamily wifi\+\_\+prov} example demonstrates the usage of {\ttfamily network\+\_\+provisioning} manager component for building a Wi-\/\+Fi provisioning application.

For this example, Bluetooth LE is chosen as the default mode of transport, over which the provisioning related communication is to take place. Nim\+BLE has been configured as the default host, but you can also switch to Bluedroid using menuconfig -\/\texorpdfstring{$>$}{>} Components -\/\texorpdfstring{$>$}{>} Bluetooth -\/\texorpdfstring{$>$}{>} Bluetooth Host.

\begin{quote}
Note\+: Since ESP32-\/\+S2 does not support Bluetooth LE, the Soft\+AP will be the default mode of transport in that case. Even for ESP32, you can change to Soft\+AP transport from menuconfig. \end{quote}


In the provisioning process the device is configured as a Wi-\/\+Fi station with specified credentials. Once configured, the device will retain the Wi-\/\+Fi configuration, until a flash erase is performed.

Right after provisioning is complete, Bluetooth LE is turned off and disabled to free the memory used by the Bluetooth LE stack. Though, that is specific to this example, and the user can choose to keep Bluetooth LE stack intact in their own application.

{\ttfamily wifi\+\_\+prov} uses the following components \+:
\begin{DoxyItemize}
\item {\ttfamily network\+\_\+provisioning} \+: Provides provisioning manager, data structures and protocomm endpoint handlers for Wi-\/\+Fi configuration
\item {\ttfamily protocomm} \+: For protocol based communication and secure session establishment
\item {\ttfamily protobuf} \+: Google\textquotesingle{}s protocol buffer library for serialization of protocomm data structures
\item {\ttfamily bt} \+: ESP-\/\+IDF\textquotesingle{}s Bluetooth LE stack for transport of protobuf packets
\end{DoxyItemize}

This example can be used, as it is, for adding a provisioning service to any application intended for IoT.

\begin{quote}
Note\+: If you use this example code in your own project, in Bluetooth LE mode, then remember to enable the BT stack and BTDM BLE control settings in your SDK configuration (e.\+g. by using the {\ttfamily sdkconfig.\+defaults} file from this project). \end{quote}

This allows the client side applications to choose the AP for which the device Wi-\/\+Fi station is to be configured. \hypertarget{README.md_autotoc_md1459}{}\doxysubsubsubsection{\texorpdfstring{Provisioning failed}{Provisioning failed}}\label{README.md_autotoc_md1459}
It is possible that the Wi-\/\+Fi credentials provided were incorrect, or the device was not able to establish connection to the network, in which the the {\ttfamily esp\+\_\+prov} script will notify failure (with reason). Serial monitor log will display the failure along with disconnect reason \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{E\ (367015)\ app:\ Provisioning\ failed!}
\DoxyCodeLine{\ \ \ \ Reason\ :\ Wi-\/Fi\ AP\ password\ incorrect}
\DoxyCodeLine{\ \ \ \ Please\ reset\ to\ factory\ and\ retry\ provisioning}

\end{DoxyCode}


Once credentials have been applied, even though wrong credentials were provided, the device will no longer go into provisioning mode on subsequent reboots until NVS is erased (see following section).\hypertarget{README.md_autotoc_md1460}{}\doxysubsubsubsection{\texorpdfstring{Provisioning does not start}{Provisioning does not start}}\label{README.md_autotoc_md1460}
If the serial monitor log shows the following \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{I\ (465)\ app:\ Already\ provisioned,\ starting\ Wi-\/Fi\ STA}

\end{DoxyCode}


it means either the device has been provisioned earlier with or without success (e.\+g. scenario covered in above section), or that the Wi-\/\+Fi credentials were already set by some other application flashed previously onto your device. On setting the log level to DEBUG this is clearly evident \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{D\ (455)\ network\_prov\_mgr:\ Found\ Wi-\/Fi\ SSID\ \ \ \ \ :\ myssid}
\DoxyCodeLine{D\ (465)\ network\_prov\_mgr:\ Found\ Wi-\/Fi\ Password\ :\ m********d}
\DoxyCodeLine{I\ (465)\ app:\ Already\ provisioned,\ starting\ Wi-\/Fi\ STA}

\end{DoxyCode}


To fix this we simple need to erase the NVS partition from flash. First we need to find out its address and size. This can be seen from the monitor log on the top right after reboot.


\begin{DoxyCode}{0}
\DoxyCodeLine{I\ (47)\ boot:\ Partition\ Table:}
\DoxyCodeLine{I\ (50)\ boot:\ \#\#\ Label\ \ \ \ \ \ \ \ \ \ \ \ Usage\ \ \ \ \ \ \ \ \ \ Type\ ST\ Offset\ \ \ Length}
\DoxyCodeLine{I\ (58)\ boot:\ \ 0\ nvs\ \ \ \ \ \ \ \ \ \ \ \ \ \ WiFi\ data\ \ \ \ \ \ \ \ 01\ 02\ 00009000\ 00006000}
\DoxyCodeLine{I\ (65)\ boot:\ \ 1\ phy\_init\ \ \ \ \ \ \ \ \ RF\ data\ \ \ \ \ \ \ \ \ \ 01\ 01\ 0000f000\ 00001000}
\DoxyCodeLine{I\ (73)\ boot:\ \ 2\ factory\ \ \ \ \ \ \ \ \ \ factory\ app\ \ \ \ \ \ 00\ 00\ 00010000\ 00124f80}
\DoxyCodeLine{I\ (80)\ boot:\ End\ of\ partition\ table}

\end{DoxyCode}


Now erase NVS partition by running the following commands \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\$IDF\_PATH/components/esptool\_py/esptool/esptool.py\ erase\_region\ 0x9000\ 0x6000}

\end{DoxyCode}
\hypertarget{README.md_autotoc_md1461}{}\doxysubsubsubsection{\texorpdfstring{Bluetooth Pairing Request during provisioning}{Bluetooth Pairing Request during provisioning}}\label{README.md_autotoc_md1461}
ESP-\/\+IDF now has functionality to enforce link encryption requirement while performing GATT write on characteristics of provisioning service. This will however result in a pairing pop-\/up dialog, if link is not encrypted. This feature is disabled by default. In order to enable this feature, please set {\ttfamily CONFIG\+\_\+\+WIFI\+\_\+\+PROV\+\_\+\+BLE\+\_\+\+FORCE\+\_\+\+ENCRYPTION=y} in the sdkconfig or select the configuration using "{}idf.\+py menuconfig"{} .
