\doxysubsection{Detailed Description}
A little fail-\/safe filesystem designed for microcontrollers.

{\bfseries{Power-\/loss resilience}} -\/ littlefs is designed to handle random power failures. All file operations have strong copy-\/on-\/write guarantees and if power is lost the filesystem will fall back to the last known good state.

{\bfseries{Dynamic wear leveling}} -\/ littlefs is designed with flash in mind, and provides wear leveling over dynamic blocks. Additionally, littlefs can detect bad blocks and work around them.

{\bfseries{Bounded RAM/\+ROM}} -\/ littlefs is designed to work with a small amount of memory. RAM usage is strictly bounded, which means RAM consumption does not change as the filesystem grows. The filesystem contains no unbounded recursion and dynamic memory is limited to configurable buffers that can be provided statically.\hypertarget{README.md_autotoc_md1515}{}\doxysubsection{\texorpdfstring{Example}{Example}}\label{README.md_autotoc_md1515}

\hypertarget{README.md_autotoc_md1516}{}\doxysubsection{\texorpdfstring{Usage}{Usage}}\label{README.md_autotoc_md1516}
Detailed documentation (or at least as much detail as is currently available) can be found in the comments in \href{lfs.h}{\texttt{ lfs.\+h}}.

littlefs takes in a configuration structure that defines how the filesystem operates. The configuration struct provides the filesystem with the block device operations and dimensions, tweakable parameters that tradeoff memory usage for performance, and optional static buffers if the user wants to avoid dynamic memory.

The state of the littlefs is stored in the {\ttfamily lfs\+\_\+t} type which is left up to the user to allocate, allowing multiple filesystems to be in use simultaneously. With the {\ttfamily lfs\+\_\+t} and configuration struct, a user can format a block device or mount the filesystem.

Once mounted, the littlefs provides a full set of POSIX-\/like file and directory functions, with the deviation that the allocation of filesystem structures must be provided by the user.

All POSIX operations, such as remove and rename, are atomic, even in event of power-\/loss. Additionally, file updates are not actually committed to the filesystem until sync or close is called on the file.\hypertarget{README.md_autotoc_md1517}{}\doxysubsection{\texorpdfstring{Other notes}{Other notes}}\label{README.md_autotoc_md1517}
Littlefs is written in C, and specifically should compile with any compiler that conforms to the {\ttfamily C99} standard.

All littlefs calls have the potential to return a negative error code. The errors can be either one of those found in the {\ttfamily enum lfs\+\_\+error} in \href{lfs.h}{\texttt{ lfs.\+h}}, or an error returned by the user\textquotesingle{}s block device operations.

In the configuration struct, the {\ttfamily prog} and {\ttfamily erase} function provided by the user may return a {\ttfamily LFS\+\_\+\+ERR\+\_\+\+CORRUPT} error if the implementation already can detect corrupt blocks. However, the wear leveling does not depend on the return code of these functions, instead all data is read back and checked for integrity.

If your storage caches writes, make sure that the provided {\ttfamily sync} function flushes all the data to memory and ensures that the next read fetches the data from memory, otherwise data integrity can not be guaranteed. If the {\ttfamily write} function does not perform caching, and therefore each {\ttfamily read} or {\ttfamily write} call hits the memory, the {\ttfamily sync} function can simply return 0.\hypertarget{README.md_autotoc_md1518}{}\doxysubsection{\texorpdfstring{Design}{Design}}\label{README.md_autotoc_md1518}
At a high level, littlefs is a block based filesystem that uses small logs to store metadata and larger copy-\/on-\/write (COW) structures to store file data.

In littlefs, these ingredients form a sort of two-\/layered cake, with the small logs (called metadata pairs) providing fast updates to metadata anywhere on storage, while the COW structures store file data compactly and without any wear amplification cost.

Both of these data structures are built out of blocks, which are fed by a common block allocator. By limiting the number of erases allowed on a block per allocation, the allocator provides dynamic wear leveling over the entire filesystem.
