(See the README.\+md file in the upper level \textquotesingle{}examples\textquotesingle{} directory for more information about examples.)

{\ttfamily thread\+\_\+prov} example demonstrates the usage of {\ttfamily network\+\_\+provisioning} manager component for building a Thread provisioning application.

For this example, Bluetooth LE is chosen as the mode of transport, over which the provisioning related communication is to take place. Nim\+BLE has been configured as the host.

In the provisioning process the device is configured as a Thread FTD with specified dataset. Once configured, the device will retain the Thread configuration, until a flash erase is performed.

Right after the provisioning is complete, Bluetooth LE is turned off and disabled to free the memory used by the Bluetooth LE stack. Though, that is specific to this example, and the user can choose to keep Bluetooth LE stack intact in their own application.

{\ttfamily thread\+\_\+prov} uses the following components \+:
\begin{DoxyItemize}
\item {\ttfamily network\+\_\+provisioning} \+: Provides provisioning manager, data structures and protocomm endpoint handlers for Thread configuration
\item {\ttfamily protocomm} \+: For protocol based communication and secure session establishment
\item {\ttfamily protobuf} \+: Google\textquotesingle{}s protocol buffer library for serialization of protocomm data structures
\item {\ttfamily bt} \+: ESP-\/\+IDF\textquotesingle{}s Bluetooth LE stack for transport of protobuf packets
\end{DoxyItemize}

This example can be used, as it is, for adding a provisioning service to any application intended for IoT.

\begin{quote}
Note\+: If you use this example code in your own project, in Bluetooth LE mode, then remember to enable the BT stack and BTDM BLE control settings in your SDK configuration (e.\+g. by using the {\ttfamily sdkconfig.\+defaults} file from this project). \end{quote}
\hypertarget{README.md_autotoc_md1430}{}\doxysubsubsection{\texorpdfstring{Security Scheme}{Security Scheme}}\label{README.md_autotoc_md1430}
The {\ttfamily protocomm} component is used for establishing secure communication channel at the time of provisioning. It supports two security schemes for establishing secure communication which are \href{https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/provisioning/provisioning.html\#security-1-scheme}{\texttt{ Security 1 Scheme}} and \href{https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/provisioning/provisioning.html\#security-2-scheme}{\texttt{ Security 2 Scheme}}. The example uses {\ttfamily Security 2 Scheme} (latest) by default.\hypertarget{README.md_autotoc_md1431}{}\doxysubsubsection{\texorpdfstring{How to use example}{How to use example}}\label{README.md_autotoc_md1431}
\hypertarget{README.md_autotoc_md1432}{}\doxysubsubsubsection{\texorpdfstring{Hardware Required}{Hardware Required}}\label{README.md_autotoc_md1432}
Example should be able to run on any commonly available ESP32-\/\+H2/\+ESP32-\/\+C6 development board.\hypertarget{README.md_autotoc_md1433}{}\doxysubsubsubsection{\texorpdfstring{Script Required}{Script Required}}\label{README.md_autotoc_md1433}
Currently, provisioning script is available for {\ttfamily Linux / Windows / mac\+OS} platforms.\hypertarget{README.md_autotoc_md1434}{}\doxysubsubsubsubsection{\texorpdfstring{Platform \+: Linux / Windows / mac\+OS}{Platform \+: Linux / Windows / mac\+OS}}\label{README.md_autotoc_md1434}

\hypertarget{README.md_autotoc_md1439}{}\doxysubsubsubsection{\texorpdfstring{Thread Scanning}{Thread Scanning}}\label{README.md_autotoc_md1439}
Provisioning manager also supports providing real-\/time Thread scan results (performed on the device) during provisioning. This allows the client side applications to choose the Thread network for which the device is to be configured. Various information about the visible Thread networks is available, like signal strength (RSSI) and link quality (LQI), etc. Also, the manager now provides capabilities information which can be used by client applications to determine availability of specific features (like {\ttfamily thread\+\_\+scan}).

\hypertarget{README.md_autotoc_md1441}{}\doxysubsubsubsection{\texorpdfstring{Sending Custom Data}{Sending Custom Data}}\label{README.md_autotoc_md1441}
The provisioning manager allows applications to send some custom data during provisioning, which may be required for some other operations like connecting to some cloud service. This is achieved by creating and registering additional endpoints using the below APIs


\begin{DoxyCode}{0}
\DoxyCodeLine{network\_prov\_mgr\_endpoint\_create();}
\DoxyCodeLine{network\_prov\_mgr\_endpoint\_register();}

\end{DoxyCode}


In this particular example, we have added an endpoint named "{}custom-\/data"{} which can be tested by passing the {\ttfamily -\/-\/custom\+\_\+data \texorpdfstring{$<$}{<}My\+Custom\+Data\texorpdfstring{$>$}{>}} option to the esp\+\_\+prov tool. Following output is expected on success\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{====\ Sending\ Custom\ data\ to\ esp32\ ====}
\DoxyCodeLine{CustomData\ response:\ SUCCESS}

\end{DoxyCode}

\hypertarget{README.md_autotoc_md1443}{}\doxysubsubsubsection{\texorpdfstring{Provisioning failed}{Provisioning failed}}\label{README.md_autotoc_md1443}
It is possible that the Thread dataset provided were incorrect, or the device was not able to establish connection to the network, in which the the {\ttfamily esp\+\_\+prov} script will notify failure (with reason). Serial monitor log will display the failure along with disconnect reason \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{E\ (367015)\ app:\ Provisioning\ failed!}
\DoxyCodeLine{\ \ \ \ Reason\ :\ Thread\ network\ not\ found}
\DoxyCodeLine{\ \ \ \ Please\ reset\ to\ factory\ and\ retry\ provisioning}

\end{DoxyCode}


Once dataset have been applied, even though wrong dataset were provided, the device will no longer go into provisioning mode on subsequent reboots until NVS is erased (see following section).\hypertarget{README.md_autotoc_md1444}{}\doxysubsubsubsection{\texorpdfstring{Provisioning does not start}{Provisioning does not start}}\label{README.md_autotoc_md1444}
If the serial monitor log shows the following \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{I\ (465)\ app:\ Already\ provisioned,\ enabling\ netif\ and\ starting\ Thread}

\end{DoxyCode}


it means either the device has been provisioned earlier with or without success (e.\+g. scenario covered in above section), or that the Thread dataset was already set by some other application flashed previously onto your device.

To fix this we simple need to erase the NVS partition from flash. First we need to find out its address and size. This can be seen from the monitor log on the top right after reboot.


\begin{DoxyCode}{0}
\DoxyCodeLine{I\ (47)\ boot:\ Partition\ Table:}
\DoxyCodeLine{I\ (50)\ boot:\ \#\#\ Label\ \ \ \ \ \ \ \ \ \ \ \ Usage\ \ \ \ \ \ \ \ \ \ Type\ ST\ Offset\ \ \ Length}
\DoxyCodeLine{I\ (58)\ boot:\ \ 0\ nvs\ \ \ \ \ \ \ \ \ \ \ \ \ \ WiFi\ data\ \ \ \ \ \ \ \ 01\ 02\ 00009000\ 00006000}
\DoxyCodeLine{I\ (65)\ boot:\ \ 1\ phy\_init\ \ \ \ \ \ \ \ \ RF\ data\ \ \ \ \ \ \ \ \ \ 01\ 01\ 0000f000\ 00001000}
\DoxyCodeLine{I\ (73)\ boot:\ \ 2\ factory\ \ \ \ \ \ \ \ \ \ factory\ app\ \ \ \ \ \ 00\ 00\ 00010000\ 00124f80}
\DoxyCodeLine{I\ (80)\ boot:\ End\ of\ partition\ table}

\end{DoxyCode}


Now erase NVS partition by running the following commands \+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\$IDF\_PATH/components/esptool\_py/esptool/esptool.py\ erase\_region\ 0x9000\ 0x6000}

\end{DoxyCode}
\hypertarget{README.md_autotoc_md1445}{}\doxysubsubsubsection{\texorpdfstring{Bluetooth Pairing Request during provisioning}{Bluetooth Pairing Request during provisioning}}\label{README.md_autotoc_md1445}
ESP-\/\+IDF now has functionality to enforce link encryption requirement while performing GATT write on characteristics of provisioning service. This will however result in a pairing pop-\/up dialog, if link is not encrypted. This feature is disabled by default. In order to enable this feature, please set {\ttfamily CONFIG\+\_\+\+WIFI\+\_\+\+PROV\+\_\+\+BLE\+\_\+\+FORCE\+\_\+\+ENCRYPTION=y} in the sdkconfig or select the configuration using "{}idf.\+py menuconfig"{} .


\begin{DoxyCode}{0}
\DoxyCodeLine{Component\ Config\ -\/-\/>\ Network\ Provisioning\ Manager\ -\/-\/>\ Force\ Link\ Encryption\ during\ Characteristic\ Read/Write}

\end{DoxyCode}
 Recompiling the application with above changes should suffice to enable this functionality.
