\doxysubsection{Detailed Description}
This example shows different techniques on how to use and extend the \doxylink{class_web_server}{Web\+Server} for specific purposes

It is a small project in it\textquotesingle{}s own and has some files to use on the web server to show how to use simple REST based services.

This example requires some space for a filesystem and runs fine on supported So\+Cs with 4 MByte or more flash by selecting the proper partition table\+:


\begin{DoxyItemize}
\item For using SPIFFS(\+Little\+FS)\+: {\ttfamily Default 4MB with spiffs (1.\+2\+MB APP/1.\+5\+MB SPIFFS)}
\item For using FATFS\+: {\ttfamily Default 4MB with ffat (1.\+2\+MB APP/1.\+5\+MB FATFS)}
\end{DoxyItemize}

It features


\begin{DoxyItemize}
\item Setup a web server
\item redirect when accessing the url with servername only
\item get real time by using builtin NTP functionality
\item send HTML responses from Sketch (see \doxylink{builtinfiles_8h}{builtinfiles.\+h})
\item use a Little\+FS file system on the data partition for static files
\item use http ETag Header for client side caching of static files
\item use custom ETag calculation for static files
\item extended File\+Server\+Handler for uploading and deleting static files
\item uploading files using drag \& drop
\item serve APIs using REST services (/api/list, /api/sysinfo)
\item define HTML response when no file/api/handler was found
\end{DoxyItemize}\hypertarget{README.md_autotoc_md612}{}\doxysubsection{\texorpdfstring{Supported Targets}{Supported Targets}}\label{README.md_autotoc_md612}

The \doxylink{class_web_server}{Web\+Server} library offers a simple path to implement a web server on a ESP32 based board.

The advantage on using the \doxylink{class_web_server}{Web\+Server} instead of the plain simple \doxylink{class_network_server}{Network\+Server} is that the \doxylink{class_web_server}{Web\+Server} takes much care about the http protocol conventions and features and allows easily access to parameters. It offers plug-\/in capabilities by registering specific functionalities that will be outlined below.\hypertarget{README.md_autotoc_md615}{}\doxysubsubsection{\texorpdfstring{Initialization}{Initialization}}\label{README.md_autotoc_md615}
In the setup() function in the webserver.\+ino sketch file the following steps are implemented to make the webserver available on the local network.


\begin{DoxyItemize}
\item Create a webserver listening to port 80 for HTTP requests.
\item Initialize the access to the filesystem in the free flash memory.
\item Connect to the local Wi-\/\+Fi network. Here is only a straight-\/forward implementation hard-\/coding network name and passphrase. You may consider to use something like the Wi\+Fi\+Manager library in real applications.
\item Register the device in DNS using a known hostname.
\item Registering several plug-\/ins (see below).
\item Starting the web server.
\end{DoxyItemize}\hypertarget{README.md_autotoc_md616}{}\doxysubsubsection{\texorpdfstring{Running}{Running}}\label{README.md_autotoc_md616}

\#\# Registering a full-\/featured handler as plug-\/in

The example also implements the class {\ttfamily File\+Server\+Handler} derived from the class {\ttfamily \doxylink{class_request_handler}{Request\+Handler}} to plug in functionality that can handle more complex requests without giving a fixed URL. It implements uploading and deleting files in the file system that is not implemented by the standard server.\+serve\+Static functionality.

This class has to implements several functions and works in a more detailed way\+:


\begin{DoxyItemize}
\item The {\ttfamily can\+Handle()} method can inspect the given http method and url to decide weather the Request\+File\+Handler can handle the incoming request or not.

In this case the Request\+File\+Handler will return true when the request method is an POST for upload or a DELETE for deleting files.

The regular GET requests will be ignored and therefore handled by the also registered server.\+serve\+Static handler.
\item The function {\ttfamily handle()} then implements the real deletion of the file.
\item The {\ttfamily can\+Upload()}and {\ttfamily upload()} methods work similar while the {\ttfamily upload()} method is called multiple times to create, append data and close the new file.
\end{DoxyItemize}

\#\# \doxylink{class_file}{File} upload

By opening \href{http://webserver/$upload.htm}{\texttt{ http\+://webserver/\$upload.\+htm}} you can easily upload files by dragging them over the drop area.

Just take the files from the data folder to create some files that can explore the server functionality.

Files will be uploaded to the root folder of the file system. and you will see it next time using \href{http://webserver/files.htm}{\texttt{ http\+://webserver/files.\+htm}}.

The filesize that is uploaded is not known when the upload mechanism in function File\+Server\+Handler\+::upload gets started.

Uploading a file that fits into the available filesystem space can be found in the Serial output\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\ txt}
\DoxyCodeLine{starting\ upload\ file\ /file.txt...}
\DoxyCodeLine{finished.}
\DoxyCodeLine{1652\ bytes\ uploaded.}

\end{DoxyCode}


Uploading a file that doesn\textquotesingle{}t fit can be detected while uploading when writing to the filesystem fails. However upload cannot be aborted by the current handler implementation.

The solution implemented here is to delete the partially uploaded file and wait for the upload ending. The following can be found in the Serial output\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\ txt}
\DoxyCodeLine{starting\ upload\ file\ /huge.jpg...}
\DoxyCodeLine{./components/esp\_littlefs/src/littlefs/lfs.c:584:error:\ No\ more\ free\ space\ 531}
\DoxyCodeLine{\ \ write\ error!}
\DoxyCodeLine{finished.}

\end{DoxyCode}


You can see on the Serial output that one filesystem write error is reported.

Please be patient and wait for the upload ending even when writing to the filesystem is disabled it maybe take more than a minute.
