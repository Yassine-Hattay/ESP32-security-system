\doxysubsection{Detailed Description}
\hypertarget{bearssl__rsa_8h_autotoc_md105}{}\doxysubsection{\texorpdfstring{RSA}{RSA}}\label{bearssl__rsa_8h_autotoc_md105}
This file documents the RSA implementations provided with Bear\+SSL. Note that the SSL engine accesses these implementations through a configurable API, so it is possible to, for instance, run a SSL server which uses a RSA engine which is not based on this code.\hypertarget{bearssl__rsa_8h_autotoc_md106}{}\doxysubsubsection{\texorpdfstring{Key Elements}{Key Elements}}\label{bearssl__rsa_8h_autotoc_md106}
RSA public and private keys consist in lists of big integers. All such integers are represented with big-\/endian unsigned notation\+: first byte is the most significant, and the value is positive (so there is no dedicated "{}sign bit"{}). Public and private key structures thus contain, for each such integer, a pointer to the first value byte ({\ttfamily unsigned char \texorpdfstring{$\ast$}{*}}), and a length ({\ttfamily size\+\_\+t}) which is the number of relevant bytes. As a general rule, minimal-\/length encoding is not enforced\+: values may have extra leading bytes of value 0.

RSA public keys consist in two integers\+:


\begin{DoxyItemize}
\item the modulus ({\ttfamily n});
\item the public exponent ({\ttfamily e}).
\end{DoxyItemize}

RSA private keys, as defined in \href{https://tools.ietf.org/html/rfc3447}{\texttt{ PKCS\#1}}, contain eight integers\+:


\begin{DoxyItemize}
\item the modulus ({\ttfamily n});
\item the public exponent ({\ttfamily e});
\item the private exponent ({\ttfamily d});
\item the first prime factor ({\ttfamily p});
\item the second prime factor ({\ttfamily q});
\item the first reduced exponent ({\ttfamily dp}, which is {\ttfamily d} modulo {\ttfamily p-\/1});
\item the second reduced exponent ({\ttfamily dq}, which is {\ttfamily d} modulo {\ttfamily q-\/1});
\item the CRT coefficient ({\ttfamily iq}, the inverse of {\ttfamily q} modulo {\ttfamily p}).
\end{DoxyItemize}

However, the implementations defined in Bear\+SSL use only five of these integers\+: {\ttfamily p}, {\ttfamily q}, {\ttfamily dp}, {\ttfamily dq} and {\ttfamily iq}.\hypertarget{bearssl__rsa_8h_autotoc_md107}{}\doxysubsubsection{\texorpdfstring{Security Features and Limitations}{Security Features and Limitations}}\label{bearssl__rsa_8h_autotoc_md107}
The implementations contained in Bear\+SSL have the following limitations and features\+:


\begin{DoxyItemize}
\item They are constant-\/time. This means that the execution time and memory access pattern may depend on the {\itshape lengths} of the private key components, but not on their value, nor on the value of the operand. Note that this property is not achieved through random masking, but "{}true"{} constant-\/time code.
\item They support only private keys with two prime factors. RSA private keys with three or more prime factors are nominally supported, but rarely used; they may offer faster operations, at the expense of more code and potentially a reduction in security if there are "{}too many"{} prime factors.
\item The public exponent may have arbitrary length. Of course, it is a good idea to keep public exponents small, so that public key operations are fast; but, contrary to some widely deployed implementations, Bear\+SSL has no problem with public exponents longer than 32 bits.
\item The two prime factors of the modulus need not have the same length (but severely imbalanced factor lengths might reduce security). Similarly, there is no requirement that the first factor ({\ttfamily p}) be greater than the second factor ({\ttfamily q}).
\item Prime factors and modulus must be smaller than a compile-\/time limit. This is made necessary by the use of fixed-\/size stack buffers, and the limit has been adjusted to keep stack usage under 2 kB for the RSA operations. Currently, the maximum modulus size is 4096 bits, and the maximum prime factor size is 2080 bits.
\item The RSA functions themselves do not enforce lower size limits, except that which is absolutely necessary for the operation to mathematically make sense (e.\+g. a PKCS\#1 v1.\+5 signature with SHA-\/1 requires a modulus of at least 361 bits). It is up to users of this code to enforce size limitations when appropriate (e.\+g. the X.\+509 validation engine, by default, rejects RSA keys of less than 1017 bits).
\item Within the size constraints expressed above, arbitrary bit lengths are supported. There is no requirement that prime factors or modulus have a size multiple of 8 or 16.
\item When verifying PKCS\#1 v1.\+5 signatures, both variants of the hash function identifying header (with and without the ASN.\+1 NULL) are supported. When producing such signatures, the variant with the ASN.\+1 NULL is used.
\end{DoxyItemize}\hypertarget{bearssl__rsa_8h_autotoc_md108}{}\doxysubsubsection{\texorpdfstring{Implementations}{Implementations}}\label{bearssl__rsa_8h_autotoc_md108}
Three RSA implementations are included\+:


\begin{DoxyItemize}
\item The {\bfseries{i32}} implementation internally represents big integers as arrays of 32-\/bit integers. It is perfunctory and portable, but not very efficient.
\item The {\bfseries{i31}} implementation uses 32-\/bit integers, each containing 31 bits worth of integer data. The i31 implementation is somewhat faster than the i32 implementation (the reduced integer size makes carry propagation easier) for a similar code footprint, but uses very slightly larger stack buffers (about 4\% bigger).
\item The {\bfseries{i62}} implementation is similar to the i31 implementation, except that it internally leverages the 64x64-\/\texorpdfstring{$>$}{>}128 multiplication opcode. This implementation is available only on architectures where such an opcode exists. It is much faster than i31.
\item The {\bfseries{i15}} implementation uses 16-\/bit integers, each containing 15 bits worth of integer data. Multiplication results fit on 32 bits, so this won\textquotesingle{}t use the "{}widening"{} multiplication routine on ARM Cortex M0/\+M0+, for much better performance and constant-\/time execution. 
\end{DoxyItemize}

Type for a private exponent computing function. 

An RSA private key ({\ttfamily \doxylink{structbr__rsa__private__key}{br\+\_\+rsa\+\_\+private\+\_\+key}}) contains two reduced private exponents, which are sufficient to perform private key operations. However, standard encoding formats for RSA private keys require also a copy of the complete private exponent (non-\/reduced), which this function recomputes.

This function suceeds if all the following conditions hold\+:


\begin{DoxyItemize}
\item Both private factors {\ttfamily p} and {\ttfamily q} are equal to 3 modulo 4.
\item The provided public exponent {\ttfamily pubexp} is correct, and, in particular, is odd, relatively prime to {\ttfamily p-\/1} and {\ttfamily q-\/1}, and greater than 1.
\item No internal storage limit is exceeded.
\end{DoxyItemize}

For all private keys produced by the key generator functions ({\ttfamily \doxylink{bearssl__rsa_8h_abe16eb51e581ad88bc8f50051969f266}{br\+\_\+rsa\+\_\+keygen}} type), this function succeeds. Note that the API restricts the public exponent to a maximum size of 32 bits.

The encoded private exponent is written in {\ttfamily d} (unsigned big-\/endian convention), and the length (in bytes) is returned. If {\ttfamily d} is {\ttfamily NULL}, then the exponent is not written anywhere, but the length is still returned. On error, 0 is returned.

Not all error conditions are detected when {\ttfamily d} is {\ttfamily NULL}; therefore, the returned value shall be checked also when actually producing the value.

uint32\+\_\+t br\+\_\+rsa\+\_\+ssl\+\_\+decrypt (\begin{DoxyParamCaption}\item[{\mbox{\hyperlink{bearssl__rsa_8h_a77085d6f13d25d5e211e6954ff30ff6a}{br\+\_\+rsa\+\_\+private}}}]{core}{, }\item[{const \mbox{\hyperlink{structbr__rsa__private__key}{br\+\_\+rsa\+\_\+private\+\_\+key}} \texorpdfstring{$\ast$}{*}}]{sk}{, }\item[{unsigned char \texorpdfstring{$\ast$}{*}}]{data}{, }\item[{size\+\_\+t}]{len}{}\end{DoxyParamCaption})}



RSA decryption helper, for SSL/\+TLS. 

This function performs the RSA decryption for a RSA-\/based key exchange in a SSL/\+TLS server. The provided RSA engine is used. The {\ttfamily data} parameter points to the value to decrypt, of length {\ttfamily len} bytes. On success, the 48-\/byte pre-\/master secret is copied into {\ttfamily data}, starting at the first byte of that buffer; on error, the contents of {\ttfamily data} become indeterminate.

This function first checks that the provided value length ({\ttfamily len}) is not lower than 59 bytes, and matches the RSA modulus length; if neither of this property is met, then this function returns 0 and the buffer is unmodified.

Otherwise, decryption and then padding verification are performed, both in constant-\/time. A decryption error, or a bad padding, or an incorrect decrypted value length are reported with a returned value of 0; on success, 1 is returned. The caller (SSL server engine) is supposed to proceed with a random pre-\/master secret in case of error.
