Select client certificate and algorithms. 

This callback function shall fill the provided {\ttfamily choices} structure with the selected algorithms and certificate chain. The {\ttfamily hash\+\_\+id}, {\ttfamily chain} and {\ttfamily chain\+\_\+len} fields must be set. If the client cannot or does not wish to send a certificate, then it shall set {\ttfamily chain} to {\ttfamily NULL} and {\ttfamily chain\+\_\+len} to 0.

The {\ttfamily auth\+\_\+types} parameter describes the authentication types, signature algorithms and hash functions that are supported by both the client context and the server, and compatible with the current protocol version. This is a bit field with the following contents\+:


\begin{DoxyItemize}
\item If RSA signatures with hash function x are supported, then bit x is set.
\item If ECDSA signatures with hash function x are supported, then bit 8+x is set.
\item If static ECDH is supported, with a RSA-\/signed certificate, then bit 16 is set.
\item If static ECDH is supported, with an ECDSA-\/signed certificate, then bit 17 is set.
\end{DoxyItemize}

Notes\+:


\begin{DoxyItemize}
\item When using TLS 1.\+0 or 1.\+1, the hash function for RSA signatures is always the special MD5+\+SHA-\/1 (id 0), and the hash function for ECDSA signatures is always SHA-\/1 (id 2).
\item When using TLS 1.\+2, the list of hash functions is trimmed down to include only hash functions that the client context can support. The actual server list can be obtained with {\ttfamily br\+\_\+ssl\+\_\+client\+\_\+get\+\_\+server\+\_\+hashes()}; that list may be used to select the certificate chain to send to the server.
\end{DoxyItemize}

Perform key exchange (client part). 

This callback is invoked in case of a full static ECDH key exchange\+:


\begin{DoxyItemize}
\item the cipher suite uses {\ttfamily ECDH\+\_\+\+RSA} or {\ttfamily ECDH\+\_\+\+ECDSA};
\item the server requests a client certificate;
\item the client has, and sends, a client certificate that uses an EC key in the same curve as the server\textquotesingle{}s key, and chooses static ECDH (the {\ttfamily hash\+\_\+id} field in the choice structure was set to -\/1).
\end{DoxyItemize}

In that situation, this callback is invoked to compute the client-\/side ECDH\+: the provided {\ttfamily data} (of length {\ttfamily \texorpdfstring{$\ast$}{*}len} bytes) is the server\textquotesingle{}s public key point (as decoded from its certificate), and the client shall multiply that point with its own private key, and write back the X coordinate of the resulting point in the same buffer, starting at offset 0. The {\ttfamily \texorpdfstring{$\ast$}{*}len} value shall be modified to designate the actual length of the X coordinate.

The callback must uphold the following\+:


\begin{DoxyItemize}
\item If the input array does not have the proper length for an encoded curve point, then an error (0) shall be reported.
\item If the input array has the proper length, then processing MUST be constant-\/time, even if the data is not a valid encoded point.
\item This callback MUST check that the input point is valid.
\end{DoxyItemize}

Returned value is 1 on success, 0 on error.

Perform a signature (client authentication). 

This callback is invoked when a client certificate was sent, and static ECDH is not used. It shall compute a signature, using the client\textquotesingle{}s private key, over the provided hash value (which is the hash of all previous handshake messages).

On input, the hash value to sign is in {\ttfamily data}, of size {\ttfamily hv\+\_\+len}; the involved hash function is identified by {\ttfamily hash\+\_\+id}. The signature shall be computed and written back into {\ttfamily data}; the total size of that buffer is {\ttfamily len} bytes.

This callback shall verify that the signature length does not exceed {\ttfamily len} bytes, and abstain from writing the signature if it does not fit.

For RSA signatures, the {\ttfamily hash\+\_\+id} may be 0, in which case this is the special header-\/less signature specified in TLS 1.\+0 and 1.\+1, with a 36-\/byte hash value. Otherwise, normal PKCS\#1 v1.\+5 signatures shall be computed.

For ECDSA signatures, the signature value shall use the ASN.\+1 based encoding.

Returned value is the signature length (in bytes), or 0 on error.
