\doxysubsection{Detailed Description}
\hypertarget{bearssl__block_8h_autotoc_md79}{}\doxysubsection{\texorpdfstring{Block Ciphers and Symmetric Ciphers}{Block Ciphers and Symmetric Ciphers}}\label{bearssl__block_8h_autotoc_md79}
This file documents the API for block ciphers and other symmetric ciphers.\hypertarget{bearssl__block_8h_autotoc_md80}{}\doxysubsubsection{\texorpdfstring{Procedural API}{Procedural API}}\label{bearssl__block_8h_autotoc_md80}
For a block cipher implementation, up to three separate sets of functions are provided, for CBC encryption, CBC decryption, and CTR encryption/decryption. Each set has its own context structure, initialised with the encryption key.

For CBC encryption and decryption, the data to encrypt or decrypt is referenced as a sequence of blocks. The implementations assume that there is no partial block; no padding is applied or removed. The caller is responsible for handling any kind of padding.

Function for CTR encryption are defined only for block ciphers with blocks of 16 bytes or more (i.\+e. AES, but not DES/3\+DES).

Each implemented block cipher is identified by an "{}internal name"{} from which are derived the names of structures and functions that implement the cipher. For the block cipher of internal name "{}\`{}xxx\`{}"{}, the following are defined\+:


\begin{DoxyItemize}
\item {\ttfamily br\+\_\+xxx\+\_\+\+BLOCK\+\_\+\+SIZE}

A macro that evaluates to the block size (in bytes) of the cipher. For all implemented block ciphers, this value is a power of two.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcenc\+\_\+keys}

Context structure that contains the subkeys resulting from the key expansion. These subkeys are appropriate for CBC encryption. The structure first field is called {\ttfamily vtable} and points to the appropriate OOP structure.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcenc\+\_\+init(br\+\_\+xxx\+\_\+cbcenc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, const void \texorpdfstring{$\ast$}{*}key, size\+\_\+t len)}

Perform key expansion\+: subkeys for CBC encryption are computed and written in the provided context structure. The key length MUST be adequate for the implemented block cipher. This function also sets the {\ttfamily vtable} field.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcenc\+\_\+run(const br\+\_\+xxx\+\_\+cbcenc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, void \texorpdfstring{$\ast$}{*}iv, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t len)}

Perform CBC encryption of {\ttfamily len} bytes, in place. The encrypted data replaces the cleartext. {\ttfamily len} MUST be a multiple of the block length (if it is not, the function may loop forever or overflow a buffer). The IV is provided with the {\ttfamily iv} pointer; it is also updated with a copy of the last encrypted block.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcdec\+\_\+keys}

Context structure that contains the subkeys resulting from the key expansion. These subkeys are appropriate for CBC decryption. The structure first field is called {\ttfamily vtable} and points to the appropriate OOP structure.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcdec\+\_\+init(br\+\_\+xxx\+\_\+cbcenc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, const void \texorpdfstring{$\ast$}{*}key, size\+\_\+t len)}

Perform key expansion\+: subkeys for CBC decryption are computed and written in the provided context structure. The key length MUST be adequate for the implemented block cipher. This function also sets the {\ttfamily vtable} field.
\item {\ttfamily br\+\_\+xxx\+\_\+cbcdec\+\_\+run(const br\+\_\+xxx\+\_\+cbcdec\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, void \texorpdfstring{$\ast$}{*}iv, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t num\+\_\+blocks)}

Perform CBC decryption of {\ttfamily len} bytes, in place. The decrypted data replaces the ciphertext. {\ttfamily len} MUST be a multiple of the block length (if it is not, the function may loop forever or overflow a buffer). The IV is provided with the {\ttfamily iv} pointer; it is also updated with a copy of the last {\itshape encrypted} block.
\item {\ttfamily br\+\_\+xxx\+\_\+ctr\+\_\+keys}

Context structure that contains the subkeys resulting from the key expansion. These subkeys are appropriate for CTR encryption and decryption. The structure first field is called {\ttfamily vtable} and points to the appropriate OOP structure.
\item {\ttfamily br\+\_\+xxx\+\_\+ctr\+\_\+init(br\+\_\+xxx\+\_\+ctr\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, const void \texorpdfstring{$\ast$}{*}key, size\+\_\+t len)}

Perform key expansion\+: subkeys for CTR encryption and decryption are computed and written in the provided context structure. The key length MUST be adequate for the implemented block cipher. This function also sets the {\ttfamily vtable} field.
\item {\ttfamily br\+\_\+xxx\+\_\+ctr\+\_\+run(const br\+\_\+xxx\+\_\+ctr\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, const void \texorpdfstring{$\ast$}{*}iv, uint32\+\_\+t cc, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t len)} (returns {\ttfamily uint32\+\_\+t})

Perform CTR encryption/decryption of some data. Processing is done "{}in place"{} (the output data replaces the input data). This function implements the "{}standard incrementing function"{} from NIST SP800-\/38A, annex B\+: the IV length shall be 4 bytes less than the block size (i.\+e. 12 bytes for AES) and the counter is the 32-\/bit value starting with {\ttfamily cc}. The data length ({\ttfamily len}) is not necessarily a multiple of the block size. The new counter value is returned, which supports chunked processing, provided that each chunk length (except possibly the last one) is a multiple of the block size.
\item {\ttfamily br\+\_\+xxx\+\_\+ctrcbc\+\_\+keys}

Context structure that contains the subkeys resulting from the key expansion. These subkeys are appropriate for doing combined CTR encryption/decryption and CBC-\/\+MAC, as used in the CCM and EAX authenticated encryption modes. The structure first field is called {\ttfamily vtable} and points to the appropriate OOP structure.
\item {\ttfamily br\+\_\+xxx\+\_\+ctrcbc\+\_\+init(br\+\_\+xxx\+\_\+ctr\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, const void \texorpdfstring{$\ast$}{*}key, size\+\_\+t len)}

Perform key expansion\+: subkeys for combined CTR encryption/decryption and CBC-\/\+MAC are computed and written in the provided context structure. The key length MUST be adequate for the implemented block cipher. This function also sets the {\ttfamily vtable} field.
\item {\ttfamily br\+\_\+xxx\+\_\+ctrcbc\+\_\+encrypt(const br\+\_\+xxx\+\_\+ctrcbc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, void \texorpdfstring{$\ast$}{*}ctr, void \texorpdfstring{$\ast$}{*}cbcmac, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t len)}

Perform CTR encryption of some data, and CBC-\/\+MAC. Processing is done "{}in place"{} (the output data replaces the input data). This function applies CTR encryption on the data, using a full block-\/size counter (i.\+e. for 128-\/bit blocks, the counter is incremented as a 128-\/bit value). The \textquotesingle{}ctr\textquotesingle{} array contains the initial value for the counter (used in the first block) and it is updated with the new value after data processing. The \textquotesingle{}cbcmac\textquotesingle{} value shall point to a block-\/sized value which is used as IV for CBC-\/\+MAC, computed over the encrypted data (output of CTR encryption); the resulting CBC-\/\+MAC is written over \textquotesingle{}cbcmac\textquotesingle{} on output.

The data length MUST be a multiple of the block size.
\item {\ttfamily br\+\_\+xxx\+\_\+ctrcbc\+\_\+decrypt(const br\+\_\+xxx\+\_\+ctrcbc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, void \texorpdfstring{$\ast$}{*}ctr, void \texorpdfstring{$\ast$}{*}cbcmac, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t len)}

Perform CTR decryption of some data, and CBC-\/\+MAC. Processing is done "{}in place"{} (the output data replaces the input data). This function applies CTR decryption on the data, using a full block-\/size counter (i.\+e. for 128-\/bit blocks, the counter is incremented as a 128-\/bit value). The \textquotesingle{}ctr\textquotesingle{} array contains the initial value for the counter (used in the first block) and it is updated with the new value after data processing. The \textquotesingle{}cbcmac\textquotesingle{} value shall point to a block-\/sized value which is used as IV for CBC-\/\+MAC, computed over the encrypted data (input of CTR encryption); the resulting CBC-\/\+MAC is written over \textquotesingle{}cbcmac\textquotesingle{} on output.

\item {\ttfamily br\+\_\+xxx\+\_\+ctrcbc\+\_\+ctr(const br\+\_\+xxx\+\_\+ctrcbc\+\_\+keys \texorpdfstring{$\ast$}{*}ctx, void \texorpdfstring{$\ast$}{*}ctr, void \texorpdfstring{$\ast$}{*}data, size\+\_\+t len)}

The \textquotesingle{}ctr\textquotesingle{} array contains the initial value for the counter (used in the first block), and it is updated with the new value after data processing.

{\bfseries{Note\+:}} DES/3\+DES nominally uses keys of 64, 128 and 192 bits (i.\+e. 8, 16 and 24 bytes), but some of the bits are ignored by the algorithm, so the {\itshape effective} key lengths, from a security point of view, are 56, 112 and 168 bits, respectively.

{\ttfamily aes\+\_\+big} is a "{}classical"{} AES implementation, using tables. It is fast but not constant-\/time, since it makes data-\/dependent array accesses.

{\ttfamily aes\+\_\+small} is an AES implementation optimized for code size. It is substantially slower than {\ttfamily aes\+\_\+big}; it is not constant-\/time either.

{\ttfamily aes\+\_\+ct} is a constant-\/time implementation of AES; its code is about as big as that of {\ttfamily aes\+\_\+big}, while its performance is comparable to that of {\ttfamily aes\+\_\+small}. However, it is constant-\/time. This implementation should thus be considered to be the "{}default"{} AES in Bear\+SSL, to be used unless the operational context guarantees that a non-\/constant-\/time implementation is safe, or an architecture-\/specific constant-\/time implementation can be used (e.\+g. using dedicated hardware opcodes).

{\ttfamily aes\+\_\+ct64} is another constant-\/time implementation of AES. It is similar to {\ttfamily aes\+\_\+ct} but uses 64-\/bit values. On 32-\/bit machines, {\ttfamily aes\+\_\+ct64} is not faster than {\ttfamily aes\+\_\+ct}, often a bit slower, and has a larger footprint; however, on 64-\/bit architectures, {\ttfamily aes\+\_\+ct64} is typically twice faster than {\ttfamily aes\+\_\+ct} for modes that allow parallel operations (i.\+e. CTR, and CBC decryption, but not CBC encryption).

{\ttfamily aes\+\_\+x86ni} exists only on x86 architectures (32-\/bit and 64-\/bit). It uses the AES-\/\+NI opcodes when available.

{\ttfamily aes\+\_\+pwr8} exists only on Power\+PC / POWER architectures (32-\/bit and 64-\/bit, both little-\/endian and big-\/endian). It uses the AES opcodes present in POWER8 and later.

{\ttfamily des\+\_\+tab} is a classic, table-\/based implementation of DES/3\+DES. It is not constant-\/time.

{\ttfamily des\+\_\+ct} is an constant-\/time implementation of DES/3\+DES. It is substantially slower than {\ttfamily des\+\_\+tab}.\hypertarget{bearssl__block_8h_autotoc_md83}{}\doxysubsubsection{\texorpdfstring{Cha\+Cha20 and Poly1305}{Cha\+Cha20 and Poly1305}}\label{bearssl__block_8h_autotoc_md83}
Cha\+Cha20 is a stream cipher. Poly1305 is a MAC algorithm. They are described in \href{https://tools.ietf.org/html/rfc7539}{\texttt{ RFC 7539}}.

Two function pointer types are defined\+:


\begin{DoxyItemize}
\item {\ttfamily \doxylink{bearssl__block_8h_a274de0985f8bb5b252a37526a9591826}{br\+\_\+chacha20\+\_\+run}} describes a function that implements Cha\+Cha20 only.
\item {\ttfamily \doxylink{bearssl__block_8h_a657418e5ad2f2667390885239ba0524d}{br\+\_\+poly1305\+\_\+run}} describes an implementation of Poly1305, in the AEAD combination with Cha\+Cha20 specified in RFC 7539 (the Cha\+Cha20 implementation is provided as a function pointer).
\end{DoxyItemize}

{\ttfamily chacha20\+\_\+ct} is a straightforward implementation of Cha\+Cha20 in plain C; it is constant-\/time, small, and reasonably fast.

{\ttfamily chacha20\+\_\+sse2} leverages SSE2 opcodes (on x86 architectures that support these opcodes). It is faster than {\ttfamily chacha20\+\_\+ct}.

{\ttfamily poly1305\+\_\+ctmul} is an implementation of the Cha\+Cha20+\+Poly1305 AEAD construction, where the Poly1305 part is performed with mixed 32-\/bit multiplications (operands are 32-\/bit, result is 64-\/bit).

{\ttfamily poly1305\+\_\+ctmul32} implements Cha\+Cha20+\+Poly1305 using pure 32-\/bit multiplications (32-\/bit operands, 32-\/bit result). It is slower than {\ttfamily poly1305\+\_\+ctmul}, except on some specific architectures such as the ARM Cortex M0+.

{\ttfamily poly1305\+\_\+ctmulq} implements Cha\+Cha20+\+Poly1305 with mixed 64-\/bit multiplications (operands are 64-\/bit, result is 128-\/bit) on 64-\/bit platforms that support such operations.

{\ttfamily poly1305\+\_\+i15} implements Cha\+Cha20+\+Poly1305 with the generic "{}i15"{} big integer implementation. It is meant mostly for testing purposes, although it can help with saving a few hundred bytes of code footprint on systems where code size is scarce.
