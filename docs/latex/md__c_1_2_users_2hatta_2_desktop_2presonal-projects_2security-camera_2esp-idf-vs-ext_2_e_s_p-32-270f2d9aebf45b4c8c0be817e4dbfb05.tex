The {\ttfamily esp\+\_\+secure\+\_\+cert} partition uses TLV format by default. TLV format has been decided based on its simplicity and efficiency. We use customized headers specifically designed for the {\ttfamily esp\+\_\+secure\+\_\+cert} partition. The {\ttfamily esp\+\_\+secure\+\_\+cert} partition is supposed to be a READ-\/only partition which can contain the data which is bound to the device and is not usually updated e.\+g. Device private key, Device certificate, CA certificate. Currently {\ttfamily esp\+\_\+secure\+\_\+cert\+\_\+mgr} component does not support modification of the {\ttfamily esp\+\_\+secure\+\_\+cert} partition.

The TLV format used in the esp\+\_\+secure\+\_\+cert partition is as follows\+:




\begin{DoxyItemize}
\item TLV header\+: It contains the information regarding the data such as the type of the data and the length of the data. For more details about the TLV, please take a look at \href{https://github.com/espressif/esp_secure_cert_mgr/tree/main/private_include/esp_secure_cert_tlv_config.h}{\texttt{ tlv\+\_\+config.\+h}}.
\begin{DoxyItemize}
\item i) TLV flags field -\/ flags byte that identifies different characteristics for the TLV
\item ii) TLV type\+: Currently the TLV format supports only a list of pre-\/defined types. The latest list for pre-\/defined types can be found at \href{https://github.com/espressif/esp_secure_cert_mgr/tree/main/private_include/esp_secure_cert_tlv_config.h}{\texttt{ tlv\+\_\+config.\+h}}. Additional custom types are also provided in order to allow storing custom data in TLV format. The custom data types can be typecasted to appropriate types after reading the TLV.
\item iii) TLV length -\/ the length of the data field in the TLV.
\end{DoxyItemize}
\item TLV footer\+: It contains the crc32 of the data and header field.
\item TLV format Padding -\/ In TLV format a padding is added automatically between the end offset of data and TLV footer. The padding is added in order to make the data field a multiple of 16 bytes which is the minimum alignment required for flash encrypted writes.
\end{DoxyItemize}\hypertarget{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1278}{}\doxysubsection{\texorpdfstring{Partition table entry}{Partition table entry}}\label{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1278}

Please note that, TLV format uses compact data representation and hence partition size is kept as 8KiB.

\begin{quote}
Note\+: The TLV read API expects that a padding of appropriate size is added to data to make it size as a multiple of 16 bytes, the partition generation utility i.\+e. \href{https://github.com/espressif/esp_secure_cert_mgr/blob/main/tools/configure_esp_secure_cert.py}{\texttt{ configure\+\_\+esp\+\_\+secure\+\_\+cert.\+py}} takes care of this internally while generating the partition. \end{quote}


When flash encryption is enabled for the device it is imporatant to encrypt the {\ttfamily esp\+\_\+secure\+\_\+cert} partition as well. Adding the encrypted flag in the partition table as done above can ensure that this is done. When flash encryption is not enabled this flag shall be ignored.\hypertarget{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1279}{}\doxysection{\texorpdfstring{TLV storage algorithms}{TLV storage algorithms}}\label{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1279}
The {\ttfamily esp\+\_\+secure\+\_\+cert\+\_\+mgr} component also supports following algorithms for TLV. In this case the TLV data is not stored directly but is stored by using one of the following algorithms. The information about the algorithms is a part of the TLV itself.


\begin{DoxyItemize}
\item HMAC based AES-\/\+GCM encryption\+: In this case the first key stored on the device with purpose {\ttfamily HMAC\+\_\+\+UP} is used to derive an AES key and the salt. This key is used to encrypt the TLV contents. This algorithm is suitable where the platform encryption is not enabled.
\item HMAC based ECDSA key derivation\+: In this case the ECDSA key is derived using following two values
\begin{DoxyItemize}
\item Salt\+: This is the salt stored in a different tlv with type {\ttfamily ESP\+\_\+\+SECURE\+\_\+\+CERT\+\_\+\+HMAC\+\_\+\+ECDSA\+\_\+\+KEY\+\_\+\+SALT}
\item HMAC key\+: This is the first key stored on the device with purpose {\ttfamily HMAC\+\_\+\+UP}. Both of these entities are used as input for the pbkdf2 algorithm to generate the ECDSA key.
\end{DoxyItemize}
\end{DoxyItemize}

Please ensure that appropriate TLV flags are enabled to take care of the underlying security configuration for the given TLV entry. On top of these security configuration, if platform flash encryption is enabled then the secure cert partition contents shall be stored in an encrypted manner on the external flash storage\hypertarget{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1280}{}\doxysection{\texorpdfstring{Legacy formats for {\ttfamily esp\+\_\+secure\+\_\+cert} partition}{Legacy formats for {\ttfamily esp\+\_\+secure\+\_\+cert} partition}}\label{md__c_1_2_users_2hatta_2_desktop_2presonal-projects_2security-camera_2esp-idf-vs-ext_2_e_s_p-32-270f2d9aebf45b4c8c0be817e4dbfb05_autotoc_md1280}
