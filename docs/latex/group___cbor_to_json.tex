\doxysubsection{Detailed Description}
Group of functions used to convert CBOR to JSON. 

This group contains two functions that can be used to convert a \doxylink{struct_cbor_value}{Cbor\+Value} object to an equivalent JSON representation. This module attempts to follow the recommendations from RFC 7049 section 4.\+1 "{}\+Converting from \+CBOR to JSON"{}, though it has a few differences. They are noted below.

These functions produce a "{}minified"{} JSON output, with no spacing, indentation or line breaks. If those are necessary, they need to be applied in a post-\/processing phase.

Note that JSON cannot support all CBOR types with fidelity, so the conversion is usually lossy. For that reason, Tiny\+CBOR supports adding a set of metadata JSON values that can be used by a JSON-\/to-\/\+CBOR converter to restore the original data types.

The Tiny\+CBOR library does not provide a way to convert from JSON representation back to encoded form. However, it provides a tool called {\ttfamily json2cbor} which can be used for that purpose. That tool supports the metadata format that these functions may produce.

Either of the functions in this section will attempt to convert exactly one \doxylink{struct_cbor_value}{Cbor\+Value} object to JSON. Those functions may return any error documented for the functions for Cbor\+Parsing. In addition, if the C standard library stream functions return with error, the text conversion will return with error Cbor\+Error\+IO.

These functions also perform UTF-\/8 validation in CBOR text strings. If they encounter a sequence of bytes that is not permitted in UTF-\/8, they will return Cbor\+Error\+Invalid\+Utf8\+Text\+String. That includes encoding of surrogate points in UTF-\/8.

\begin{DoxyWarning}{Warning}
The metadata produced by these functions is not guaranteed to remain stable. A future update of Tiny\+CBOR may produce different output for the same input and parsers may be unable to handle it.
\end{DoxyWarning}

\doxysubsubsection*{Conversion limitations}

When converting from CBOR to JSON, there may be information loss. This section lists the possible scenarios.

\begin{DoxyParagraph}{Number precision\+:}
ALL JSON numbers, due to its Java\+Script heritage, are IEEE 754 double-\/precision floating point. This means JSON is not capable of representing all integers numbers outside the range \mbox{[}-\/(2\textsuperscript{53})+1, 2\textsuperscript{53}-\/1\mbox{]} and is not capable of representing NaN or infinite. If the CBOR data contains a number outside the valid range, the conversion will lose precision. If the input was NaN or infinite, the result of the conversion will be the JSON null value. In addition, the distinction between half-\/, single-\/ and double-\/precision is lost.
\end{DoxyParagraph}
\begin{DoxyParagraph}{}
If enabled, the original value and original type are stored in the metadata.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Non-\/native types\+:}
CBOR\textquotesingle{}s type system is richer than JSON\textquotesingle{}s, which means some data values cannot be represented when converted to JSON. The conversion silently turns them into strings\+: CBOR simple types become "{}simple(nn)"{} where {\ttfamily nn} is the simple type\textquotesingle{}s value, with the exception of CBOR undefined, which becomes "{}undefined"{}, while CBOR byte strings are converted to an Base16, Base64, or Base64url encoding
\end{DoxyParagraph}
\begin{DoxyParagraph}{}
If enabled, the original type is stored in the metadata.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Presence of tags\+:}
JSON has no support for tagged values, so by default tags are dropped when converting to JSON. However, if the Cbor\+Convert\+Obey\+Byte\+String\+Tags option is active (default), then certain known tags are honored and are used to format the conversion of the tagged byte string to JSON.
\end{DoxyParagraph}
\begin{DoxyParagraph}{}
If the Cbor\+Convert\+Tags\+To\+Objects option is active, then the tag and the tagged value are converted to a JSON object. Otherwise, if enabled, the last (innermost) tag is stored in the metadata.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Non-\/string keys in maps\+:}
JSON requires all Object keys to be strings, while CBOR does not. By default, if a non-\/string key is found, the conversion fails with error Cbor\+Error\+Json\+Object\+Key\+Not\+String. If the Cbor\+Convert\+Stringify\+Map\+Keys option is active, then the conversion attempts to create a string representation using Cbor\+Pretty. Note that the {\ttfamily json2cbor} tool is not able to parse this back to the original form.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Duplicate keys in maps\+:}
Neither JSON nor CBOR allow duplicated keys, but current Tiny\+CBOR does not validate that this is the case. If there are duplicated keys in the input, they will be repeated in the output, which many JSON tools may flag as invalid. In addition to that, if the Cbor\+Convert\+Stringify\+Map\+Keys option is active, it is possible that a non-\/string key in a CBOR map will be converted to a string form that is identical to another key.
\end{DoxyParagraph}
\begin{DoxyParagraph}{}
When metadata support is active, the conversion will add extra key-\/value pairs to the JSON output so it can store the metadata. It is possible that the keys for the metadata clash with existing keys in the JSON map. 
\end{DoxyParagraph}
