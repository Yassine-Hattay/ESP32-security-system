\doxysubsection{Detailed Description}
\hypertarget{bearssl__ec_8h_autotoc_md84}{}\doxysubsection{\texorpdfstring{Elliptic Curves}{Elliptic Curves}}\label{bearssl__ec_8h_autotoc_md84}
This file documents the EC implementations provided with Bear\+SSL, and ECDSA.\hypertarget{bearssl__ec_8h_autotoc_md85}{}\doxysubsubsection{\texorpdfstring{Elliptic Curve API}{Elliptic Curve API}}\label{bearssl__ec_8h_autotoc_md85}
Only "{}named curves"{} are supported. Each EC implementation supports one or several named curves, identified by symbolic identifiers. These identifiers are small integers, that correspond to the values registered by the \href{http://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml\#tls-parameters-8}{\texttt{ IANA}}.

Since all currently defined elliptic curve identifiers are in the 0..31 range, it is convenient to encode support of some curves in a 32-\/bit word, such that bit x corresponds to curve of identifier x.

An EC implementation is incarnated by a {\ttfamily \doxylink{structbr__ec__impl}{br\+\_\+ec\+\_\+impl}} instance, that offers the following fields\+:


\begin{DoxyItemize}
\item {\ttfamily supported\+\_\+curves}

A 32-\/bit word that documents the identifiers of the curves supported by this implementation.
\item {\ttfamily generator()}

Callback method that returns a pointer to the conventional generator point for that curve.
\item {\ttfamily order()}

Callback method that returns a pointer to the subgroup order for that curve. That value uses unsigned big-\/endian encoding.
\item {\ttfamily xoff()}

Callback method that returns the offset and length of the X coordinate in an encoded point.
\item {\ttfamily mul()}

Multiply a curve point with an integer.
\item {\ttfamily mulgen()}

Multiply the curve generator with an integer. This may be faster than the generic {\ttfamily mul()}.
\item {\ttfamily muladd()}

Multiply two curve points by two integers, and return the sum of the two products.
\end{DoxyItemize}

All curve points are represented in uncompressed format. The {\ttfamily mul()} and {\ttfamily muladd()} methods take care to validate that the provided points are really part of the relevant curve subgroup.

For all point multiplication functions, the following holds\+:


\begin{DoxyItemize}
\item Functions validate that the provided points are valid members of the relevant curve subgroup. An error is reported if that is not the case.
\item Processing is constant-\/time, even if the point operands are not valid. This holds for both the source and resulting points, and the multipliers (integers). Only the byte length of the provided multiplier arrays (not their actual value length in bits) may leak through timing-\/based side channels.
\item The multipliers (integers) MUST be lower than the subgroup order. If this property is not met, then the result is indeterminate, but an error value is not necessarily returned.
\end{DoxyItemize}\hypertarget{bearssl__ec_8h_autotoc_md86}{}\doxysubsubsection{\texorpdfstring{ECDSA}{ECDSA}}\label{bearssl__ec_8h_autotoc_md86}
ECDSA signatures have two standard formats, called "{}raw"{} and "{}asn1"{}. Internally, such a signature is a pair of modular integers {\ttfamily (r,s)}. The "{}raw"{} format is the concatenation of the unsigned big-\/endian encodings of these two integers, possibly left-\/padded with zeros so that they have the same encoded length. The "{}asn1"{} format is the DER encoding of an ASN.\+1 structure that contains the two integer values\+: \begin{DoxyVerb}ECDSASignature ::= SEQUENCE {
    r   INTEGER,
    s   INTEGER
}
\end{DoxyVerb}


In general, in all of X.\+509 and SSL/\+TLS, the "{}asn1"{} format is used. Bear\+SSL offers ECDSA implementations for both formats; conversion functions between the two formats are also provided. Conversion of a "{}raw"{} format signature into "{}asn1"{} may enlarge a signature by no more than 9 bytes for all supported curves; conversely, conversion of an "{}asn1"{} signature to "{}raw"{} may expand the signature but the "{}raw"{} length will never be more than twice the length of the "{}asn1"{} length (and usually it will be shorter).

Note that for a given signature, the "{}raw"{} format is not fully deterministic, in that it does not enforce a minimal common length.

Compute EC public key from EC private key. 

This function uses the provided elliptic curve implementation ({\ttfamily impl}) to compute the public key corresponding to the private key held in {\ttfamily sk}. The public key point is written into {\ttfamily kbuf}, which is then linked from the {\ttfamily \texorpdfstring{$\ast$}{*}pk} structure. The size of the public key point, i.\+e. the number of bytes used in {\ttfamily kbuf}, is returned.

If {\ttfamily kbuf} is {\ttfamily NULL}, then the public key point is NOT computed, and the public key structure {\ttfamily \texorpdfstring{$\ast$}{*}pk} is unmodified ({\ttfamily pk} may be {\ttfamily NULL} in that case). The size of the public key point is still returned.

If {\ttfamily pk} is {\ttfamily NULL} but {\ttfamily kbuf} is not {\ttfamily NULL}, then the public key point is computed and stored in {\ttfamily kbuf}, and its size is returned.

If the curve used by the private key is not supported by the curve implementation, then this function returns zero.

The private key MUST be valid. An off-\/range private key value is not necessarily detected, and leads to unpredictable results.
